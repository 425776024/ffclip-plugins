# HTML 上下文超时恢复

`HTML 渲染超时：Target.createBrowserContext` 表示本机 Chromium 没有在 15 秒内回复创建隔离上下文的命令。原实现仅拒绝当前命令，保留原连接；后续排队的预览、导出或清理请求可能继续等待同一失效连接。源内容不断变化时，原 LRU 策略还会反复销毁、重建浏览器上下文。

本次修改：

- 最多保留八个隔离页面。换源时关闭旧 target，复用空闲上下文并创建新 target，重置脚本全局状态。
- 命令超时、连接断开或私有浏览器退出时，立即拒绝该连接的所有待处理命令，禁止继续发送。两条捕获通道共用一次浏览器重建，各自重试原时间点一次。
- 模板脚本错误直接报告；取消后不自动重试。等待页面锁的请求在分配资源前检查取消。
- 关闭先中止待处理命令，再等待队列排空；同时关闭共享同一过程，已经因信号退出的子进程不会继续等待另一个退出事件。

2026-10-02 本机验证：

- 六项传输与生命周期测试覆盖超时清空待处理命令、清理不再额外等待、双通道合并重建、有限重试、取消、启动期间关闭，以及 24 次换源只创建八个上下文。
- 真实 Chromium 中故意不发送首次 `Target.createBrowserContext` 数据包，让生产代码的 15 秒超时实际触发。确认旧私有进程退出、两条任务共用一个新进程，0.25/0.5 秒的原始透明像素、位置和时间点均正确。
- 真实 Chromium 并发进行 24 次源变化后，读取 CDP 确认八个隔离上下文、八个 HTML page target；target ID 与页面池一致，每个页面的脚本全局计数重新从 1 开始。Chromium 自带的 `browser_ui` target 单独统计。
- 46 项相关回归测试通过，包括 HTML/GSAP 模板、前后 seek、透明像素、缓存、取消和客户端资源释放；另单独执行上述真实 15 秒超时测试通过。
- 完整构建、271 个 npm 发布文件检查通过。使用构建后的服务及编辑器完成重型花字＋HTML＋视频的默认导出：1920×1080、30 fps、6 秒，H.264/AAC，180 帧，约 8.62 秒。FFmpeg 全部解码 180 个视频帧通过。

运行证据保存在 `.local/qa/html-recovery/` 的 `tests.log`、`real-timeout.log`、`build.log`、`package.log` 和 `packaged-results.json`。这次通过可控故障验证恢复流程，没有复现用户项目自然发生超时的底层 Chromium 条件。

服务端代码需要重新启动本地服务才能生效；仅刷新编辑器不会替换已有的 Chromium 连接。
