# 导出并行准备实测（2026-10-02）

重型花字导出启用现有的两个 native worker，提前准备最多六个后续源帧请求；HTML 动画提前请求最多两张原尺寸截图。准备工作与当前帧的 GPU 合成、编码重叠，最终帧仍按时间顺序提交，并遵守编码器和写文件背压。音频混合/编码原本就与视频任务并行。

本机 Chrome 154、1920×1080、30fps、6 秒项目的真实 MP4 导出结果如下，全部为浏览器编码，180 帧写出完整。

| 场景                   |           顺序准备 |    并行/提前准备 | 结果                                                             |
| ---------------------- | -----------------: | ---------------: | ---------------------------------------------------------------- |
| HTML＋视频             |   4.385 / 3.496 秒 | 2.315 / 2.319 秒 | 对照末轮的热运行减少约 34%；首轮还包含初次媒体、字体、编码器工作 |
| 四字重花字＋HTML＋视频 | 15.327 / 15.228 秒 | 7.715 / 7.658 秒 | 平均 15.278→7.686 秒，耗时减少 49.7%，约 1.99 倍吞吐             |

每组按关闭、开启、开启、关闭顺序运行。重花字组两边都开启 HTML 提前准备，只切换花字 worker，因此其加速不混入 HTML 优化。HTML 内容在每轮附加无视觉效果的独立注释，让已缓存截图不能被计入收益。计时从 `renderVideo` 调用开始，包含创建导出、worker 初始化、源帧准备、合成、编码、写文件和最终 receipt；不包括随后验证和清理。分辨率、帧率、模板、布局、字体、素材、码率均相同。

## 画面与资源验证

- 对照同一 WASM 原生花字的三个 1080p RGBA 样本，以及开启实际提前准备后的三个完整 WebGPU 合成画面；每次直接比较 8,294,400 字节，六次差异字节数均为 0，完整合成时观察到两个 worker。
- 两组优化后的真实 MP4 各取 1.1、2、2.5、4.4、5.8 秒解码帧，以实际 PTS 渲染参考图。HTML＋视频 MAE 为 0.092–0.161 / 255；花字混合项目为 0.104–0.500 / 255。视频为有损编码，这些误差不代表原始 RGBA 有差异。
- 构建后的编辑器通过默认导出流程实际写出同一重花字工程，用时 8.14 秒，界面显示“导出完成”；全部八个对照成品及该构建成品都由 FFmpeg 完整解码，FFprobe 确认各有 180 帧、1920×1080，包含 AAC 音频。
- 每个花字缓存与 HTML 提前准备缓存分别保留最多 64 MiB 的 RGBA；这不是整个浏览器、WASM heap 或 GPU 的总内存上限。HTML 最多两张，花字最多两个 worker；取消、源变化、离开片段时回收过期预测和图像，预测在作品结束处停止。
- 40 项源生命周期、缓存、几何、音频时序、花字 worker、HTML 提前准备测试通过；另有实际 Chromium HTML/GSAP 运行时和编辑器导出完成窗口验证。完整构建通过。
- npm 打包内容检查通过，验证了 271 个发布文件；本次没有发布到 npm。

花字 worker 当前覆盖非 external 的 flower-style-03 / flower-style-38 及其组合；其他模板继续走既有渲染路径，worker 传输不可用时也退回该路径。真实模板/资源错误仍使导出失败。`htmlPrefetch: false`、`textWorkers: false` 仅用于精确输入的顺序对照和兼容诊断，不需要用户在界面配置。

这是本机、小型固定项目的实测，尚未验证 4K、长视频、多种系统/浏览器或用户当前慢项目的全部组合。可核查数值、source SHA-256、原始像素对照与成品路径见 [export-performance-results.json](export-performance-results.json)。本机复现辅助脚本和详细原始报告保存在 `.local/qa/export-speed`，素材来自既有固定工程 `.local/html-evidence/performance-fixed-quality-session.json`。
